### 1. 比赛定位偏移与 RTK/GNSS 干扰

**现象**：2025 年比赛中 GPS 信号偏移了十几米。

#### 1.1 原文原因分析（待验证，保留现场异议）

```
2025 年实际配置: 单频 GPS + RTK + 4Hz dronekit
RTK 修正数据走 900MHz 数传 → ISM 免授权频段 → 极易被干扰

如果 RTK 数传被干扰 → RTK Fixed/Float 失败 → 回落到单频单点定位:
  单频单点: 水平 ±2-5m, 垂直 ±5-10m
  叠加 4Hz 更新量化 ±2.5m
  RSS 综合误差 ≈ ±6.7m

  这和偏移十几米完全吻合！（±6.7m 是 1σ，2σ 就是 ±13.4m）
  【现场补充：纯扯淡，就是被干扰了，当时水平偏移15-20m】

关键证据:
  - 如果 RTK 正常工作（±2cm），不可能出现十几米偏移
  - 如果 GPS 本身被干扰（丢星），飞控会触发 failsafe，不会正常飞行
  - 最合理的解释: RTK 数传被干扰 → 静默降级为单频单点 → 精度暴跌但飞控不报警
  - RTK 数传走 900MHz ISM → 和其他队伍数传同频段 → 互相干扰概率很高
```

#### 1.2 原文精度对比（待验证）

```
                    水平精度          垂直精度
  RTK Fixed:        ±2cm             ±3cm
  RTK Float:        ±20-50cm         ±50cm
  单点(单频L1):      ±2-5m            ±5-10m
  单点(双频L1+L5):   ±1-2m            ±3-5m
  单点+SBAS/PPP:     ±0.5-1m          ±1-3m
```

#### 1.3 原文误差估算：30 m 投放（待验证）

使用 trajectory.py 的实际参数（m=0.35kg, Cd=0.47, A=0.005m²）仿真：

**弹道基本数据**（30m 高度）：

| 飞行速度 | 水平飞行距离 | 落地时间 |
|---------|------------|---------|
| 15 m/s | 35.1 m | 2.55 s |
| 20 m/s | 46.1 m | 2.57 s |

**GPS 高度误差对水平落点的影响**（30m, 20m/s）：

```
弹道计算用 GPS 报告的高度预测投弹点。如果 GPS 高度有误差:

  GPS报25m(实际30m) → 预测水平距=42.4m, 偏差=-3.7m  ← 提前投弹，落短
  GPS报27m(实际30m) → 预测水平距=43.9m, 偏差=-2.2m
  GPS报29m(实际30m) → 预测水平距=45.4m, 偏差=-0.7m
  GPS报30m(实际30m) → 预测水平距=46.1m, 偏差=0m     ← 正确
  GPS报31m(实际30m) → 预测水平距=46.8m, 偏差=+0.7m
  GPS报33m(实际30m) → 预测水平距=48.2m, 偏差=+2.1m
  GPS报35m(实际30m) → 预测水平距=49.5m, 偏差=+3.4m  ← 延迟投弹，过远

规律: 每 1m 高度误差 → ~0.7m 水平落点偏差（在 30m/20m/s 条件下）
```

**综合投弹误差对比**（30m 高度, 20m/s, RSS 组合）：

| 方案 | GPS水平 | 高度→水平 | 频率量化 | **RSS总误差** |
|------|---------|----------|---------|--------------|
| 2025实际（4Hz + RTK被干扰→单频单点） | ±3m | ±5.5m | ±2.5m | **±6.7m** |
| EKF 50Hz + 双频单点（无RTK） | ±1.5m | ±3.4m | ±0.2m | **±3.7m** |
| EKF 50Hz + 双频单点 + **激光测高** | ±1.5m | ±0.1m | ±0.2m | **±1.5m** |
| EKF 50Hz + RTK | ±0.05m | ±0.05m | ±0.2m | **±0.2m** |

**核心发现**：
1. **去年 ±6.7m（1σ）≈ 2σ 时可达 ±13m，完美解释十几米偏移**
2. 不用 RTK，只靠双频 GPS + 激光测高 → **±1.5m**，已经实用
3. **激光测高是关键**：消除了高度误差（从 ±3.4m 降到 ±0.1m），投弹精度提升 2.5 倍
4. 30m 高度投弹的主要误差源是**高度不准**（占 RSS 的 90%+），不是水平不准

#### 1.4 后续优化方案：高度源与激光测高（待验证）

```
GPS 垂直精度 ≈ 水平精度 × 1.5~3 倍（几何精度因子 VDOP > HDOP）

原因: GPS 卫星都在头顶半球，垂直方向几何构型天然差:
  - 水平: 四面八方都有卫星 → 三角测量好
  - 垂直: 没有"脚底下"的卫星 → 单侧观测，精度差

单点 GPS 垂直精度 ~3-5m → 对投弹和降落都是灾难:
  - 投弹: 30m/20m/s 下 3m 高度误差 → 2.1m 水平落点偏差
  - 降落: 飞控以为在 3m 高度，实际可能在 6m 或 0m → flare 时机完全错误
```

**解法：激光测距仪**

| 传感器 | 量程 | 精度 | 重量 | 价格 | 适用 |
|--------|------|------|------|------|------|
| TFmini-S | 12m | ±1cm | 5g | ~100元 | ✅ **首选** |
| TF-Luna | 8m | ±2cm | 5g | ~80元 | ✅ 够用 |
| TF02-Pro | 40m | ±1cm | 12g | ~300元 | ✅ 高度余量大 |
| Garmin LIDAR-Lite v4 | 10m | ±1cm | 17g | ~500元 | ✅ ArduPilot 原生支持 |

```
激光测高 + GPS 水平 = 完美互补:

  水平定位: GPS 单点 ~1-2m（够用，降落跑道宽 >10m）
  垂直定位: 激光测距 ±1cm（12m 以内极精准）

ArduPilot 原生支持:
  - RNGFND_LANDING = 1  → 降落时自动使用测距仪替代 GPS 高度
  - 在 flare 阶段用激光测距触发拉平 → 精度远超 GPS/气压计
  - 需设置: RNGFND_TYPE, RNGFND_MIN_CM, RNGFND_MAX_CM, RNGFND_GNDCLEAR

降落流程:
  GPS 引导 → 进入跑道上空 → 下降到 12m 以下 → 激光测距接管垂直 → 精准 flare
```

#### 1.5 原文风险分析：GPS 信号干扰（待验证）

GPS 信号到达地面极其微弱（~-130 dBm），比 4G 基站弱 60dB，容易被干扰：

```
干扰类型:
  1. 宽带压制: 覆盖 L1/L2/L5 → 完全丢星
  2. 窄带干扰: 只干扰 L1 → 双频接收机可切 L5 继续工作
  3. 欺骗(Spoofing): 假 GPS 信号 → 位置偏移但不报警

比赛中概率:
  - 故意干扰 GPS = 影响所有队伍 + 可能影响机场运行 → 风险极高，不太可能
  - 意外干扰: 其他队伍电子设备无意辐射 → 可能但范围小
  - 使用屏蔽器: 可能干扰自己和周围队伍 GPS → 有前例

固定翼特殊困难:
  - 不能悬停 → 光流方案价值有限
  - 必须持续飞行 → IMU 漂移积累更快
  - 降落需精准对准跑道 → 没 GPS 几乎不可能自主降落
```

**降级策略**：

| 策略 | 续航时间 | 精度 | 适用场景 |
|------|---------|------|---------|
| EKF IMU 惯性推算 | 10~30s | 快速发散 | 短暂 GPS 丢失 |
| 预存航线 + IMU | ~1-2min | 发散 ~50-100m | 紧急返航 |
| **切手动接管** | — | — | **保底方案** |

#### 1.6 后续优化方案汇总（待验证）

```
弃用 RTK 完全可行:
  - 水平: 双频 GPS（u-blox F9P 单点模式）~1-2m，够用
  - 垂直: TFmini-S 激光测距（5g/100元/±1cm），12m 内精准
  - 省掉 RTK 基站（几千~万元）+ 数传电台 → 减少干扰点和故障源

必做:
  1. 双频 GPS 模块（u-blox F9P），提高单点精度 + 抗窄带干扰
  2. 激光测距仪，解决垂直精度 + 精准降落
  3. 配置 ArduPilot failsafe: GPS 丢失 → RTL 或切手动
  4. 安全员准备随时切手动接管

可选:
  5. 双 GPS 模块冗余（~1000元）
  6. 抗干扰天线 CRPA（价格高，固定翼集成困难）
```

### 2. 罗盘、IMU 与布线干扰

#### 2.1 2025 问题记录

- 罗盘（Compass）开机后无法自动校准，航向持续旋转漂移，无法稳定
- IMU（惯性测量单元）开机时如果飞机有震动，初始姿态会有 5 度左右角度误差
- 机体内部布线混乱：Jetson、交换机、树莓派、PWM 信号线、1W 5.8G 数传线等高频/大电流线缠绕在一起
- 机场电磁环境复杂，存在强干扰源

#### 2.2 原文原因假设（待验证）

1. **罗盘磁干扰严重**
  - 电源线、高频信号线靠近罗盘，产生强磁场，导致校准失败、航向漂移
  - 5.8G 数传发射功率高（1W），靠近罗盘时磁场/射频干扰极大
  - 机场环境有其他队伍/设备的强电磁辐射

2. **IMU 初始姿态误差**
  - 开机时飞机震动，IMU 零偏未能正确初始化，导致初始角度有偏差
  - IMU 安装位置未避开振动源（如电机、舵机）

3. **布线混乱导致耦合干扰**
  - 电源线、信号线、射频线未分层/分区布置，互相耦合
  - Jetson/交换机/树莓派等设备工作时大电流脉冲，产生瞬态磁场

4. **机场电磁环境复杂**
  - 多队伍设备同场工作，存在大功率数传、图传、遥控等多种射频源
  - 机场本身可能有雷达、基站等强干扰源

#### 2.3 后续优化建议
[核心]：增加外置罗盘和imu：固定在原理天线和线材的位置

- 罗盘远离高频/大电流线，单独引线，必要时加磁屏蔽
- IMU 固定于远离振动源位置，开机静置 5 秒完成初始化
- 机体内部布线分层、分区，电源/信号/射频线分开走线，必要时加屏蔽层
- 赛前用地磁计/频谱仪检测机场环境，避开强干扰区
- 5.8G 数传天线远离罗盘/IMU，必要时降低发射功率

### 3. GPS 丢失后的任务鲁棒性

**核心原因：飞控惯性推算（Dead Reckoning）位置漂移 1~5m/s**

#### 3.1 侦察阶段

| 丢星时长 | 位置误差 | 时间对齐 | 影响 |
|----------|---------|---------|------|
| 10s | 10~50m | 正常（<1ms 漂移） | 反解坐标偏差大，被 DBSCAN 过滤 |
| 20s | 20~100m | 正常（<2ms 漂移） | 完全不可信，被 DBSCAN 过滤 |
| >100s | >100m | 接近对齐阈值 | 数据全部无效 |

**有缓解机制**：DBSCAN 聚类（eps=7m, min_samples=5）天然将漂移期数据标记为噪声过滤。只要 GPS 恢复后有足够的正常数据，不影响最终定位。

#### 3.2 投弹阶段

**无缓解机制**。如果投弹阶段 GPS 丢失，位姿完全不可信，只能依赖飞控 failsafe（如 RTL）。

#### 3.3 后续优化方向

- 侦察阶段：当前 DBSCAN 已足够，可以在 YOLO 反解前加 GPS 质量检查（`vehicle.gps_0.fix_type`），丢星时直接跳过反解
- 投弹阶段：加 GPS 状态检查，丢星时中止投弹并进入备用逻辑（如转为打默认坐标或 RTL）

### 4. 投放精度与位姿更新频率

**核心原因：位姿数据更新慢且有延时，投弹判断的时间分辨率不够**

#### 4.1 2025 状态（初始状态）

`drop_and_land()` 直接读 dronekit 的 `vehicle` 对象进行投弹判断（`trajectory.calculate_bomb_trajectory(attack_point, vehicle)`）。**没有使用 EKF 插值**，原开发者注明原因：EKF 链路延时大、位姿数据频率低（4Hz）、没时间调参。

投弹循环是 tight loop，但 dronekit 回调更新仅 ~4Hz（250ms），两次更新之间 `dis` 值不变化：
```python
if not (last_dis == dis):
    # 只有dronekit收到mavlink数据更新后，才能计算出不同的dis
```

**2025 方案误差量化（20m/s 飞行速度）**

| 误差源 | 量级 | 说明 |
|--------|------|------|
| 4Hz 位置量化 | ±5m | **主要误差**，250ms 内位置不更新 |
| MAVLink 通信延时 ~15ms | ~0.3m | vehicle 直读延时较短 |
| 舵机响应延时 ~50ms | ~1m | 机械延时 |
| **合计** | **~5~8m** | |

#### 4.2 原文归因：MAVLink 输入频率（待验证）

`set_data_stream_rates()` 设置 `SR0_POSITION=5`、`SR0_EXTRA1=10`，但 dronekit 回调实测只有 ~4Hz。README 明确记录：

> 飞控usb口的数据流频率参数不论怎么设置，用dronekit回调实测都是4hz

这是所有实时性问题的根源——不论 Jetson 端怎么优化，输入只有 4Hz。

#### 4.3 后续方案 A：LinearEKF 与 50 Hz 输出（待验证）

改 `drop_and_land()` 投弹判断为 `calculate_bomb_trajectory2(attack_point, pose)`，使用 EKF 输出的位姿，同时将 `pose_fps` 提高到 50Hz。

**改动量极小**，核心只改两处：
```python
# config json: "pose_fps": 50

# drop_and_land() 中投弹判断:
# 原: dis = trajectory.calculate_bomb_trajectory(attack_point, vehicle)
# 改: dis = trajectory.calculate_bomb_trajectory2(attack_point, pose) if pose else dis
```

**原开发者三个顾虑的回应：**

**顾虑1：EKF 链路延时比 vehicle 直读大**

```
                    数据年龄最优        数据年龄最差          
vehicle 直读         ~15ms              ~265ms (等下次MAVLink) → 20m/s下 5.3m
EKF 50Hz            ~25ms              ~35ms                  → 20m/s下 0.7m
EKF 100Hz           ~20ms              ~25ms                  → 20m/s下 0.5m
```

50Hz 下 EKF 最差延时 35ms，远优于 vehicle 直读最差 265ms。**EKF 的确定性延时小，vehicle 直读的不确定性大。** 问题在于当时 10Hz 时 EKF 最差延时确实是 115ms，开发者的判断在那个频率下是对的。

延时组成：
```
飞控传感器 → MAVLink → USB → dronekit回调    时延1: ~15ms
    → measurement_queue → EKF处理             时延2: ~1ms
    → 等待next_output_time                    时延3: 0~20ms (50Hz)
    → pose_queue → 消费                       时延4: ~几ms
总延时: ~25~35ms
```

**顾虑2：位姿数据频率低（4Hz），EKF 主要靠外推**

4Hz 输入 + 50Hz 输出 = 每 12~13 个输出中只有 1 个有真实测量，其余是 `predict_with_dt()` 匀速外推。

但投弹航线是**直线匀速飞行**，LinearEKF 匀速假设完全成立：

| 误差源 | 250ms 外推累积误差 | 说明 |
|--------|-------------------|------|
| 速度波动 ±0.5m/s（风扰） | ±0.125m | 极小 |
| 航向变化 ±1°/s（微修正） | ~0.4m（100m 落点处） | 可接受 |
| **外推总误差** | **~0.5m** | 远小于当前 5m 量化误差 |

**顾虑3：没时间调 EKF**

LinearEKF **不需要调参**。它本质就是"最近一次测量值 + 匀速外推"，没有 Q/R 矩阵。只有 PoseEKF（完整扩展卡尔曼滤波）才需要调参。

**下策误差量化（20m/s）**

| 误差源 | 量级 | 对比 2025 |
|--------|------|----------|
| 50Hz 时间量化 | ±0.4m | 5m → 0.4m ✅ |
| EKF 链路延时 ~35ms | ~0.7m | 可由 correction_t 补偿 |
| 匀速外推误差 | ~0.5m | 投弹直线段可接受 |
| 舵机响应 ~50ms | ~1m | 可由 correction_t 补偿 |
| **合计（补偿后）** | **~1m** | **从 5~8m 降至 ~1m** |

#### 4.4 后续方案 B：提高 MAVLink 输入频率（待验证）

绕过 dronekit 瓶颈，从根本上获得更高频率的真实测量数据。

| 方案 | 预期频率 | 复杂度 | 效果 |
|------|---------|--------|------|
| TELEM 串口 + pymavlink | 10~50Hz | 中等 | EKF 外推比例大幅降低，精度真正提升 |
| 飞控 Lua 脚本推送 | 50Hz+ | 较高 | 最优输入频率 |

注意：需要验证飞控是否会过载（README 中提到的风险）。此方案与下策可叠加——先实现下策（零风险），再尝试上策。

2026 修正：如果投弹判断已迁移到飞控内部 100Hz Lua 脚本，则提高机载 Python 侧 MAVLink 位姿频率不再是投弹主线任务。它仍然有价值，但定位为**侦察阶段有效数据质量优化支线**：

- 目标：把 `GLOBAL_POSITION_INT` / `ATTITUDE` 等真实测量输入从约 4Hz 拉高到 20-50Hz。
- 收益：减少 LinearEKF 外推比例，提高每张照片反解时的位姿新鲜度。
- 优先级：低于相机参数、模型识别率、ROI 双阶段识别、locate 标定和 Lua 投弹标定。
- 验收：必须用日志统计真实 measurement 频率、pose 到最近 measurement 的时间差、反解坐标散布，不能只看 `pose_fps` 配置值。

##### 4Hz 根因分析

ArduPilot 官方文档（[Requesting Data From The Autopilot](https://ardupilot.org/dev/docs/mavlink-requesting-data.html)）明确指出：

> **If you find the message rates are reverting to some fixed rate (often 4hz)** after you set them, **it is probably a Ground Control station adjusting the rates.**

这就是 4Hz 的真正原因。dronekit 内部使用过时的 `REQUEST_DATA_STREAM` 方法请求数据流，它会覆盖 `SRx_` 参数设置。同时如果有 GCS（如 Mission Planner、QGC）连接在同一链路上，GCS 也会周期性发送 `REQUEST_DATA_STREAM` 把速率压回预设值（通常就是 4Hz）。

此外 dronekit **项目已基本停止维护**（PyPI 版本停留在 Python 2 时代，GitHub 420+ open issues，无活跃维护者），其内部消息处理线程本身可能也有性能瓶颈。

##### 提频方案对比

**方案 ①：pymavlink + `SET_MESSAGE_INTERVAL`（推荐，改动最小）**

直接用 pymavlink 替代 dronekit 的消息接收部分，使用 ArduPilot 4.0+ 支持的 `MAV_CMD_SET_MESSAGE_INTERVAL` 命令精确控制单条消息速率：

```python
# 请求 GLOBAL_POSITION_INT(id=33) 以 50Hz 发送
connection.mav.command_long_send(
    target_system, target_component,
    mavutil.mavlink.MAV_CMD_SET_MESSAGE_INTERVAL, 0,
    33,      # message_id: GLOBAL_POSITION_INT
    20000,   # interval_us: 20ms = 50Hz
    0, 0, 0, 0, 0)

# 请求 ATTITUDE(id=30) 以 50Hz 发送
connection.mav.command_long_send(
    target_system, target_component,
    mavutil.mavlink.MAV_CMD_SET_MESSAGE_INTERVAL, 0,
    30,      # message_id: ATTITUDE
    20000,   # interval_us: 20ms = 50Hz
    0, 0, 0, 0, 0)
```

同时需要在飞控端设置 `SERIAL0_OPTIONS` 的 bit12（Ignore Streamrate）防止 GCS 覆盖。

| 项目 | 说明 |
|------|------|
| 预期频率 | 单条消息可达 50Hz（需验证 USB 带宽和飞控负载） |
| 改动量 | 中等：替换 navigate.py 中的 dronekit 消息监听为 pymavlink |
| 风险 | 低：pymavlink 是 ArduPilot 官方维护的库 |
| 注意 | dronekit 的 `vehicle.commands`、`vehicle.mode` 等功能仍需保留，可混用 |
| 硬件 | 仍用 USB 口，V5 Nano USB 理论带宽远超 MAVLink 所需 |

**方案 ②：SD 卡配置文件固定消息速率**

ArduPilot 支持在 SD 卡根目录放置 `message-intervals-chan0.txt`：
```
30 20
33 20
```
表示 ATTITUDE(30) 和 GLOBAL_POSITION_INT(33) 以 20ms（50Hz）间隔发送。此方法在飞控启动时即生效，不受 GCS 干扰。

| 项目 | 说明 |
|------|------|
| 改动量 | 极小：只放一个文件到 SD 卡 |
| 风险 | 极低 |
| 限制 | 仍需 Jetson 端能跟上接收（dronekit 可能仍有处理瓶颈），建议配合 pymavlink |

**方案 ③：Lua 脚本设置消息速率**

ArduPilot 提供官方示例脚本 `message_interval.lua`，在飞控端设置速率。效果与方案②类似，但更灵活（可运行时动态调整）。

**方案 ④：MAVROS（ROS1）**

MAVROS 是 ROS1 的 MAVLink 桥接包，底层用 pymavlink + boost 实现，支持高频率消息订阅。

| 项目 | 说明 |
|------|------|
| 预期频率 | 可达 50Hz+（取决于飞控端配置） |
| 改动量 | **大**：需要在 Jetson 上安装 ROS1，重构消息接收为 ROS topic 订阅 |
| 优势 | 成熟的时间同步（`/mavros/timesync`）、丰富的消息类型封装 |
| 劣势 | ROS1 已进入维护模式（EOL 2025），Jetson JetPack 不预装 ROS，引入重量级依赖 |
| **结论** | **不推荐**。对本项目而言是杀鸡用牛刀，且 ROS1 已过时 |

**方案 ⑤：XRCE-DDS Agent + ROS2（ArduPilot 原生 DDS）**

ArduPilot 4.5+ 内置 AP_DDS 库，通过 Micro-XRCE-DDS 协议直接发布 ROS2 topic，**完全绕过 MAVLink**。

```
飞控内部传感器 → AP_DDS → XRCE-DDS协议(串口/UDP) → Micro-XRCE-DDS Agent → ROS2 Topic
```

| 项目 | 说明 |
|------|------|
| 预期频率 | 可达 50~200Hz（飞控内部 EKF 输出频率） |
| 改动量 | **极大**：需要 ROS2 Humble 环境 + Agent 进程 + 重写所有消息处理为 ROS2 subscriber |
| 优势 | 绕过 MAVLink 瓶颈，数据直接从飞控 EKF 输出，延时最低 |
| 劣势 | V5 Nano 需要确认固件版本是否支持 AP_DDS（需 4.5+），串口资源分配复杂 |
| **结论** | **长期最优方案，但短期改动量太大**，且 CUAV V5 Nano 固件版本需要确认 |

**方案 ⑥：换 PX4 固件**

PX4 原生支持 DDS（uXRCE-DDS），内部 uORB 消息总线频率极高（IMU 可达 1kHz），且 PX4 的 ROS2 集成更成熟。

| 项目 | 说明 |
|------|------|
| 预期频率 | DDS topic 可达 100Hz+ |
| 改动量 | **灾难级**：换固件 = 全部飞控参数重调 + 所有 MAVLink 代码重写 + PID 重调 + 航线格式变化 |
| **结论** | **完全不推荐**。V5 Nano 调好的 ArduPilot 参数和航线逻辑全部作废 |

##### 提频方案推荐路径

```
立即可做（零风险）：
  ① SD卡放 message-intervals-chan0.txt 固定消息速率
  + dronekit 端设置 SERIAL0_OPTIONS bit12 忽略 GCS streamrate 覆盖

短期（1~2周）：
  ② pymavlink 替代 dronekit 的消息监听（保留 dronekit 的 vehicle 做任务上传等）
  + SET_MESSAGE_INTERVAL 请求 50Hz

长期（如有需要）：
  ③ XRCE-DDS + ROS2（仅在上述方案仍不满足精度要求时考虑）

不推荐：
  ✗ MAVROS（ROS1 已过时，重依赖）
  ✗ PX4（换固件代价太大）
```

#### 4.5 后续方案 C：飞控端 Lua 投放（待验证）

将投弹判断从 Jetson 移到飞控端执行，完全消除通信延时：

```
当前: 飞控传感器 → MAVLink → Jetson计算 → MAVLink投弹指令 → 飞控执行
Lua:  飞控传感器 → Lua脚本直接计算 → 直接控制舵机
```

- 飞控内部传感器数据可达 400Hz，零通信延时
- 延时仅剩舵机响应 ~50ms
- **但复杂度最高**：需要在飞控端用 Lua 实现弹道计算，调试困难，且受飞控 CPU 限制

2026 修正：若 Lua 脚本已确定作为投弹主线，则投弹阶段不再依赖 Jetson/树莓派侧 DroneKit 4Hz 位姿，也不依赖图像-pose 对齐或 4G 识别延时。投弹风险应重新排序为：

1. Lua 弹道模型是否与 `trajectory.py` 等价或经过重新标定。
2. 舵机/机械释放延时是否标定。
3. 飞控内部高度源是否可靠，最好结合激光测高。
4. 目标坐标是否由侦察阶段稳定反解和聚类得到。
5. 风场、空速/地速估计和进入投弹航线的姿态是否稳定。

## 二、P1：数据质量与精度标定

<a id="issue-5"></a>

### 5. 图像与位姿对齐

**原结论：EKF 输出频率（10Hz）低，图像对齐命中率仅 ~20%。**

**修正结论：该 20% 结论只在“图像时间戳相对 pose 100ms 网格随机分布”的假设下成立。2025 实际系统若使用 RTK/GPS PPS 或 TIMEPULSE 直接降压到 3.3V 触发全局快门，并且照片文件名正确记录该硬件触发时刻，则照片应天然落在统一 Unix 100ms 时间网格上；`pose_fps=10` 的 EKF 输出也会落在 100ms 网格上。此时图像-pose 时间戳对齐率理论上应接近 100%。**

#### 5.1 原文现象与机制说明（待验证）

`detect_aligner()` 用双指针匹配图像和位姿的时间戳，阈值 ±10ms。EKF 每 100ms 输出一个 pose，图像必须恰好落在 ±10ms 窗口内：

```
命中窗口 = 2 × 10ms = 20ms
pose 间隔 = 100ms（10Hz）
命中率 ≈ 20%  →  ~80% 图像被丢弃
```

上述推导作为历史分析保留，但它的前提是图像时间戳在 100ms 周期内随机分布。若照片由 GPS 硬件脉冲触发，实际问题不再是随机命中率，而是**固定相位与时间戳记录是否正确**：

```
同相:   照片 ...000/...100/...200，pose ...000/...100/...200 → 接近 100%
偏 50ms:照片 ...050/...150/...250，pose ...000/...100/...200 → 可能接近 0%
```

#### 5.2 原文影响分析（待验证）

- 如果硬件触发与 pose 网格同相，则不会大量丢图，对齐率不是主要瓶颈。
- DroneKit 约 4Hz 仍会降低真实 measurement 密度，使 10Hz pose 中一部分依赖 LinearEKF 外推。
- 侦察阶段飞机速度约 10-20m/s，姿态相对平稳，且反解是队列式离线匹配；在这种条件下 LinearEKF 外推误差可能不大。

#### 5.3 后续优化方案

| 方案 | 目标 | 优先级 |
|------|------|--------|
| 验证 PPS/TIMEPULSE 触发相位 | 确认照片真实曝光时刻与文件名时间戳是否同相 | 最高 |
| 统计 `image_timestamp % 100` 与 `pose_timestamp % 100` | 判断 20% 假设是否成立 | 最高 |
| 统计 pose 到最近真实 measurement 的时间差 | 判断 4Hz 输入造成的有效位姿质量损失 | 高 |
| `pymavlink SET_MESSAGE_INTERVAL` 提高 pose 输入频率 | 提高侦察阶段有效数据质量 | 次要支线 |
| 改 aligner 为相邻 pose 线性插值 | 消除固定相位偏差对阈值匹配的影响 | 备选 |

**需要实际情况检验**：必须用真实飞控、真实相机触发和实飞/滑行日志统计后再定性。不能仅根据 `pose_fps=10` 和 `ALIGN_THRESHOLD=10ms` 推出 20% 对齐率。

### 6. 释放延时补偿标定

**现象**

`trajectory.py` 中 `correction_t` 补偿投弹系统延时，当前配置值为 **0**：

```json
"drop": { "correction_t": 0, "servo_channel": 9 }
```

补偿逻辑：弹道计算时将水平起点前移 `x += correction_t * vx`。

**待标定内容**

| 架构方案 | 需补偿的延时 | 估计值 | 20m/s 下偏差 |
|---------|------------|--------|-------------|
| 2025 vehicle 直读 | MAVLink ~15ms + 舵机 ~50ms | ~0.065s | ~1.3m |
| 下策 EKF 50Hz | EKF链路 ~35ms + 舵机 ~50ms | ~0.085s | ~1.7m |

### 7. 完整 PoseEKF 的调参与验证

**现象**

代码中实现了两个 EKF：
- `LinearEKF`：匀速外推 + 直接赋值更新，**零调参**，当前在用
- `PoseEKF`：基于 filterpy 的完整 EKF，需要调 Q（过程噪声）和 R（测量噪声）矩阵

navigate.py 中注释标记：
```python
ekf = LinearEKF() # attention 是否要用PoseEFK? 需要测试
```

- PoseEKF 在**转弯、加减速**段理论上更优（能利用状态转移模型平滑预测）
- 但投弹段是匀速直线，LinearEKF 假设完全成立，PoseEKF 无明显优势
- PoseEKF 调参不当反而可能引入发散或过度滤波
- **优先级低于投弹架构优化**，建议在下策落地后再考虑尝试
