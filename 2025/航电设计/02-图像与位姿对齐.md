## 1. 数据流概览

```
飞控(ArduPilot) ─MAVLink/USB─▶ navigate.py ─回调─▶ measurement_queue ─EKF插值─▶ pose_queue ──┐
                                                                                                ▼
                                                                                    detect_aligner()
                                                                                    时间戳对齐(±10ms)
                                                                                                ▲
树莓派 ─NFS写图─▶ picture_nfs/                                                                 │
树莓派 ─MQTT───▶ mqtt_receiver.py ─读图+时间戳─▶ image_queue ─────────────────────────────────┘
                                                        │
                                                        ▼
                                                  yolo识别 + 位姿反解
                                                        │
                                                        ▼
                                                  target_queue → DBSCAN聚类 → 投弹坐标
```

## 2. 两条时间链路

<a id="alignment-3"></a>

### 2.1 飞控侧（位姿数据）

**时钟源**：GPS卫星原子钟 → 飞控GPS模块 → `SYSTEM_TIME` MAVLink消息

**流程**：
1. 飞控通过USB串口以MAVLink协议发送数据，`navigate.py`用dronekit `connect()`连接飞控
2. 注册三个MAVLink回调：
   - `handle_system_time`：接收`SYSTEM_TIME`消息，建立 **boot_ms ↔ unix_usec** 锚点映射（存入`time_ref`）
   - `handle_global_position`：接收GPS位置+速度（lat, lon, alt, vn, ve, vd），通过`calculate_unix_time()`换算为Unix微秒时间戳，放入`measurement_queue`
   - `handle_attitude`：接收姿态（roll, pitch, yaw），同样换算时间戳后放入`measurement_queue`
3. EKF插值线程（`run_ekf_interpolation`）从`measurement_queue`按时间顺序取出数据，用`LinearEKF`融合插值，以固定频率（`pose_fps`）输出9维位姿数据，打包为`pose_data` dict放入`pose_queue`

**时间戳换算公式**（`calculate_unix_time`）：
```python
unix_usec = time_ref['unix_usec'] + (time_boot_ms - time_ref['boot_ms']) * 1000
```

**关键概念**：

| 时间戳 | 含义 | 硬件源 | 起点 |
|--------|------|--------|------|
| `time_boot_ms` | 飞控上电后MCU内部定时器累加的毫秒数 | MCU晶振(HSE/HSI) → SysTick | 上电=0 |
| `time_unix_usec` | GPS同步的UTC绝对时间（微秒） | GPS卫星原子钟 | 1970-01-01 UTC |

两者通过`SYSTEM_TIME`消息建立锚点，本质是**用GPS原子钟校准MCU晶振的相对时间**。

<a id="alignment-4"></a>

### 2.2 树莓派侧（图像数据）

**时钟源**：GPS卫星 → 树莓派GPS模块 + PPS硬件脉冲 → gpsd/chrony同步系统时钟

**流程**：
1. 树莓派/相机侧接收RTK/GPS输出的PPS或TIMEPULSE硬件脉冲。2025 实际接线中，该脉冲经电平转换/降压到 3.3V 后直接接入全局快门触发引脚，因此真实曝光时刻由GPS硬件时间脉冲决定，而不是普通软件定时决定。

> 另一版本原文的触发说明：
>
> 1. 树莓派接收PPS（每秒脉冲）信号作为硬件触发拍照，生成精确UTC时间戳
2. 照片以毫秒时间戳命名（如`1695123456789.jpg`），通过NFS写入Jetson的`picture_nfs/`目录
3. 树莓派通过MQTT发送文件名到Jetson
4. `mqtt_receiver.py`的`on_message`回调收到MQTT消息后，从`picture_nfs/`读取图片，用`cv2.imread`加载（旋转180°适配安装角度），连同毫秒时间戳打包为`{'timestamp': ms, 'frame': image}`放入`image_queue`

注意区分两个时间：

| 时间 | 来源 | 说明 |
|------|------|------|
| 真实曝光时刻 | RTK/GPS PPS 或 TIMEPULSE 硬件脉冲 | 精度最高，是物理采样时刻 |
| 文件名时间戳 | 树莓派软件记录/对齐后的 Unix ms | detect 使用的是这个值；必须确认它准确代表硬件触发时刻 |

如果文件名时间戳由软件回调生成，即使真实曝光由硬件 PPS 触发，也仍需验证回调延迟、四舍五入策略和 100ms 网格相位是否正确。

## 3. 对齐机制

**对齐发生在`detect.py`的`detect_aligner()`函数中。**

<a id="alignment-6"></a>

### 算法：双指针时间戳匹配

```python
ALIGN_THRESHOLD = 10  # 阈值 ±10ms

diff = current_image_ms - current_pose['timestamp']

if diff > ALIGN_THRESHOLD:
    # 图像比位姿新太多 → 丢弃旧位姿，取下一个pose
    current_pose = None
elif diff < -ALIGN_THRESHOLD:
    # 位姿比图像新太多 → 丢弃旧图像，取下一张image
    current_image_ms = None
else:
    # |diff| ≤ 10ms → 匹配成功
    yolo.run_yolo_detection(timestamp, pose, frame, ...)
```

<a id="alignment-7"></a>

### 涉及的队列

| 队列 | 生产者 | 消费者 | 内容 |
|------|--------|--------|------|
| `measurement_queue` | navigate.py MAVLink回调 | `run_ekf_interpolation`线程 | (unix_us, 类型, 位置/姿态数据) |
| `pose_queue` | `run_ekf_interpolation`线程 | `detect_aligner` | `{'timestamp': ms, 'lat', 'lon', 'alt', 'roll', 'pitch', 'yaw', ...}` |
| `image_queue` | `mqtt_receiver.py` | `detect_aligner` | `{'timestamp': ms, 'frame': cv2图像}` |
| `target_queue` | `yolo.run_yolo_detection` | `detect_receiver` | `{'lat', 'lon', 'pattern_id'}` |

<a id="alignment-8"></a>

### 时间基准统一的前提

两侧都源自**GPS卫星UTC时间**，经过不同路径：
- 飞控：GPS → `SYSTEM_TIME` → boot_ms偏移换算
- 树莓派：GPS + PPS → chrony/gpsd → 系统时钟 → 文件名

GPS同步精度通常 ~100ns，远优于10ms对齐阈值。

<a id="alignment-9"></a>

### 关于“10Hz pose 只有 20% 对齐率”的修正

如果图像时间戳相对 100ms pose 网格是随机分布，则 `ALIGN_THRESHOLD=±10ms` 的命中窗口只有 20ms，理论命中率约 20%。这个推导只适用于**随机时间戳假设**。

2025 实际系统若使用 RTK/GPS PPS 或 TIMEPULSE 直接硬触发全局快门，并且文件名时间戳正确落在 Unix 100ms 网格上，则图像时间戳不是随机分布，而是：

```
照片: ...000ms, ...100ms, ...200ms, ...
pose:  ...000ms, ...100ms, ...200ms, ...
```

此时 `pose_fps=10` 并不天然导致 20% 对齐率；对齐率理论上应接近 100%。真正需要检查的是固定相位：

```
同相:   照片 ...000/...100/...200，pose ...000/...100/...200 → 接近 100%
偏 50ms:照片 ...050/...150/...250，pose ...000/...100/...200 → 可能接近 0%
```

因此 2025 对齐问题不能只靠公式判断，必须用日志验证。

## 4. 误差分析

<a id="alignment-11"></a>

### 4.1 正常工作时

| 误差源 | 量级 | 影响 |
|--------|------|------|
| GPS卫星时钟精度 | ~100ns | 可忽略 |
| 树莓派PPS同步精度 | <1μs | 可忽略 |
| 飞控SYSTEM_TIME刷新间隔（~1s） | MCU晶振漂移 ±50ppm × 1s = ±50μs | 可忽略 |
| EKF输出频率量化误差 | 若图像时间戳随机，最大 1/(2×pose_fps) 秒（如10Hz→50ms）；若 PPS 硬触发且与 pose 同相，量化误差接近 0 | 取决于硬件触发相位和文件名时间戳是否正确 |
| DroneKit真实测量频率 | 实测约 4Hz | 不一定降低时间戳对齐率，但会降低有效位姿测量密度，使部分 10Hz pose 依赖 LinearEKF 外推 |

<a id="alignment-12"></a>

### 另一版本的原始误差判断（历史表述，后文附修正）

| 误差源 | 量级 | 影响 |
|---|---|---|
| EKF输出频率量化误差 | 最大 1/(2×pose_fps) 秒（如10Hz→50ms） | **这是最大误差源**，但被10ms阈值限制 |

**正常时总对齐误差 < 10ms，满足任务需求。**

<a id="alignment-13"></a>

### 后续修正与验证建议

**修正结论：正常时总对齐误差是否 <10ms，取决于 PPS/TIMEPULSE 触发相位、文件名时间戳记录方式和 EKF pose 输出网格是否同相。若同相，对齐率应接近 100%；若固定相位偏差超过 10ms，则可能大量对齐失败。**

对侦察阶段而言，DroneKit 4Hz 的主要影响不是“对齐不上”，而是“pose 真实测量密度低”。在 10-20m/s、直线平稳侦察段，LinearEKF 外推误差可能可接受，但需要实测验证。

建议日志验收项：

| 检查项 | 目的 |
|--------|------|
| `image_timestamp % 100` | 确认照片文件名是否落在 100ms 网格 |
| `pose_timestamp % 100` | 确认 EKF 输出是否落在同一 100ms 网格 |
| `abs(image_timestamp - nearest_pose_timestamp)` | 统计真实对齐误差 |
| `pose_timestamp - nearest_measurement_timestamp` | 统计 pose 到最近真实 MAVLink 测量的时间差，评估外推比例 |
| 同一目标反解坐标散布 | 判断 4Hz 输入 + LinearEKF 外推是否足够 |

<a id="alignment-14"></a>

### 4.2 GPS丢失场景

> 【待实测的原文分析】以下保留原判断、数值表和推导，不将其视为本次整理已验证的性能。原文后续验证要求一并保留。

<a id="alignment-15"></a>

#### PPS与拍照

u-blox F9P（CUAV 9PS内核）在丢星后进入Holdover模式，PPS继续由TCXO驱动输出。

**结论：GPS丢失10~20s，PPS仍在输出，树莓派继续拍照。**

<a id="alignment-16"></a>

#### 时间戳漂移

| 丢星时长 | 树莓派时间戳漂移(±20~50ppm) | 飞控SYSTEM_TIME漂移(±50ppm) | 合计最大漂移 | 对齐(阈值10ms) |
|----------|---------------------------|---------------------------|-------------|----------------|
| 10s | ±0.2~0.5ms | ±0.5ms | ~1ms | **正常** |
| 20s | ±0.4~1.0ms | ±1.0ms | ~2ms | **正常** |
| 60s | ±1.2~3.0ms | ±3.0ms | ~6ms | **接近阈值** |
| 200s | ±4~10ms | ±10ms | ~20ms | **对齐失败** |

<a id="alignment-17"></a>

#### 真正的瓶颈：位置精度

GPS丢失后飞控EKF进入惯性推算（Dead Reckoning），位置漂移速率约1~5m/s：

| 丢星时长 | 位置误差 | 对YOLO反解的影响 |
|----------|---------|-----------------|
| 10s | 10~50m | 反解坐标偏差大，不可信 |
| 20s | 20~100m | 完全不可信 |

**短期丢星(10~20s)时间对齐不是瓶颈，位置精度才是真正的问题。**

好在DBSCAN聚类（eps=7m, min_samples=5）天然能将GPS漂移期的低质量数据标记为噪声点(label=-1)过滤掉。

<a id="alignment-18"></a>

### 4.3 总结

```
短期GPS丢失(10~20s):
  ├─ 时间对齐: ✅ 正常（漂移<2ms，远小于10ms阈值）
  ├─ 拍照触发: ✅ PPS仍在输出
  ├─ 位置精度: ❌ 漂移10~100m，反解不可信
  └─ 最终影响: DBSCAN聚类过滤噪声 → 对最终投弹坐标影响有限

长期GPS丢失(>100s):
  ├─ 时间对齐: ⚠️ 漂移接近/超过阈值
  ├─ 位置精度: ❌ 完全不可用
  └─ 最终影响: 该段数据全部无效
```

## 5. 后续架构迁移时的结论更新（原文）

- 侦察阶段：若 PPS/TIMEPULSE 硬触发、文件名时间戳和 EKF pose 网格同相，图像-pose 对齐不是主瓶颈。重点应放在相机标定、畸变、安装角、模型识别率、ROI 两阶段识别、多帧投票和 DBSCAN 聚类。
- 位姿频率：DroneKit 4Hz 会降低有效测量密度，但在侦察直线平稳段不一定致命。可以把 `pymavlink SET_MESSAGE_INTERVAL` 提高位姿输入频率作为次要支线任务，用于提升反解稳定性。
- 投弹阶段：若采用飞控内部 100Hz Lua 脚本投弹，则投弹不再依赖 Jetson/树莓派侧 DroneKit 4Hz 和图像-pose 对齐。主要风险转为 Lua 弹道模型、释放延时、高度源和风场补偿。
- 必须实测：以上结论需要真实硬件触发、真实飞控输出和飞行/滑行日志验证，不能只由文档或配置推断。
